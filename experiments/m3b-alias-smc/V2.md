# Revision 2: distinguish ordinary A from fused A+B

The first OFF capture was stopped at the SUB-complete gate because the host
required a strictly newer A generation in both arms. Its eight ADD and eight
SUB results were correct, the RX/RW bytes matched the expected opcode change,
and both pagemap entries identified PFN 0x1e7e3. Ordinary A remained owner
0x96f2e40, code 0x96f2f00, generation 0x13bf2, physical PC 0x1e7e3004. The
ordinary A block's instructions did not change when only B was patched.

The [retained failure decision](../../artifacts/m3b-alias-smc-off-failure-01/decision.json)
binds the original frozen source, failed capture and successful failure replay.
No V1 ON capture is attempted. This is an incorrect OFF oracle expectation,
not evidence that correct ordinary execution must rebuild A after changing B.

Revision 2 retains exactly the same guest code, arithmetic cases, opcode stores,
physical identity requirements, six gates, three reset epochs, runtime settings
and deadlines. OFF permits an unchanged ordinary A owner while requiring all
actual arithmetic and physical/code-byte checks. ON still requires a strictly
newer fused generation, different code and owner identities, and positive
compiled fused execution after each B patch. The fused translator checks its
complete A+B extent (`tb->size == plan.bytes`), so this ON expectation is retained.

A new frozen source and image build precede one fresh OFF and one ON capture.
No failed source or capture is overwritten. Synthetic tests explicitly accept
a stable ordinary OFF A generation while retaining all stale-ON rejection tests.
The separately authored Python implementation must make the same distinction.
