# Separate sustained protocol after MSG2 screen01

The original screen failed selection and remains a failed screen: SHA candidate/control median ratio 0.8478, integer 1.0048, JSON 1.2436 and HTTP 0.9792. This decision does not reinterpret that result or authorize the old eight-pair confirmation. Raw inputs and a rehashed descriptive review are retained in [the screen analysis](../../artifacts/m2-screen-analysis-01/analysis.json) and [warmup review](../../artifacts/m2-screen-warmup-review-01.json).

The endpoint intervals were still changing substantially. Last/first batch ratios for control/candidate were integer 0.807/0.714, JSON 0.533/0.765, SHA 0.783/0.741 and HTTP 0.736/0.609. Control JSON also rose 13.5% from its second to third batch. The first/last pattern is evidence against treating the three batches as a settled plateau; it is not evidence that the secondary regression was solely noise or solely insufficient warmup.

Stopped charged-instance counts grew from 10572 after control warmup to 11402, and 10723 to 11582 for the candidate. The unchanged runtime increases admission requirements at 9600, 10800 and 11400 charged instances. Thus substantial timing changes coexist with movement through admission regimes. These are net pool counts, not emitted-code bytes or a direct attribution of the elapsed changes. Each phase observed 2 GiB linear memory. The host's recorded free-memory/load samples and the separately observed 12 GiB compiler VM motivate stronger host isolation. The approximately 13 GiB compressor observation was made after the screen; it does not establish compressor usage during either timed run. Guest time is not used to correct host elapsed time.

PLAN 16.2 separates fixed-warmup throughput from sustained execution and requires reporting continued JIT/pool growth. The new `defuss-m2-sustained-v2` protocol therefore has a new bundle, compatibility identity, validator, campaign and analyzer. The original operation source, inputs, results, runtime bytes, VM flags and all decision margins remain unchanged. It uses five fixed 100-call warmup rounds per endpoint, then eight measured 100-call batches per endpoint; every batch and stopped pool observation is retained. Balanced endpoint orders repeat twice during measurement. Four fresh exploratory pairs alternate AB/BA, without adaptive stopping or selective exclusions.

The analysis compares all-eight-batch endpoint medians at the independent pair level. A predeclared 10% early-half/late-half ratio bound can veto the entire campaign's suitability; it cannot discard or rerun individual completed VMs. Confirmation size is calculated prospectively from the four-pair log-ratio variance using a conservative upper 90% SD bound and fixed design effects, then frozen. The minimum is 8 pairs and the predeclared feasible maximum 32; an estimate above the maximum blocks confirmation rather than reducing N or relaxing a margin. The calculation is approximate and does not guarantee power for the paired bootstrap.

The compiler VM must report `Stopped` before and after every fresh run using a hash-pinned status executable and exact VM identity. Builds, packaging and diagnostic guests remain serial with measurements. Full protocol and planning details, executable commands and limitations are in [the sustained-v2 harness](../../benchmarks/harness/m2-sustained-v2/README.md). No sustained result is claimed by this plan; its first real exploration is still required.
